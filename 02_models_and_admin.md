# Part 2: Models and the Admin Site

## What Are Models?

In Django, a **model** is a Python class that defines the structure of a database table. Each attribute of the class represents a column in the table. Django's **ORM (Object-Relational Mapper)** translates between Python objects and SQL queries — you never write raw SQL.

```
Python Class (Model)          ←→        Database Table
─────────────────────                   ──────────────────
class InterestTopic:                    CREATE TABLE trivia_interesttopic (
    label = CharField()                     id INTEGER PRIMARY KEY,
    weight = FloatField()                   label VARCHAR(100),
    user = ForeignKey()                     weight REAL,
                                            user_id INTEGER REFERENCES auth_user(id)
                                        );
```

### Why not write SQL directly?

| Approach | Pros | Cons |
|----------|------|------|
| Raw SQL | Maximum control, can use any database feature | Database-specific, error-prone, no migration tracking |
| Django ORM | Database-agnostic, type-safe, auto-migrations | Can't express every possible query; learning curve |
| SQLAlchemy | More flexible than Django ORM | Not integrated with Django's admin, auth, etc. |

Django's ORM is the right choice here because it integrates with the admin site, migrations, and authentication — all features we need.

## Writing the Models

Open `trivia/models.py` and replace its contents:

```python
from django.conf import settings
from django.db import models


class WatchHistoryEntry(models.Model):
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="watch_history"
    )
    video_title = models.CharField(max_length=500)
    channel_name = models.CharField(max_length=255, blank=True)
    watched_at = models.DateTimeField(null=True, blank=True)
    raw_category = models.CharField(max_length=100, blank=True)

    def __str__(self):
        return f"{self.video_title[:50]} ({self.channel_name})"


class InterestTopic(models.Model):
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="interests"
    )
    label = models.CharField(max_length=100)
    weight = models.FloatField(default=0.0)

    class Meta:
        ordering = ["-weight"]

    def __str__(self):
        return f"{self.label} ({self.weight:.2f}) - {self.user}"


class Question(models.Model):
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="questions"
    )
    topic = models.ForeignKey(
        InterestTopic,
        on_delete=models.CASCADE,
        related_name="questions"
    )
    prompt_text = models.TextField()
    options = models.JSONField()
    correct_answer = models.CharField(max_length=255)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.prompt_text[:60]


class QuizAttempt(models.Model):
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name="quiz_attempts"
    )
    started_at = models.DateTimeField(auto_now_add=True)
    completed_at = models.DateTimeField(null=True, blank=True)
    score = models.IntegerField(default=0)

    def __str__(self):
        return f"Attempt by {self.user} on {self.started_at:%Y-%m-%d}"


class Answer(models.Model):
    attempt = models.ForeignKey(
        QuizAttempt,
        on_delete=models.CASCADE,
        related_name="answers"
    )
    question = models.ForeignKey(
        Question,
        on_delete=models.CASCADE
    )
    selected_answer = models.CharField(max_length=255)
    is_correct = models.BooleanField(default=False)

    def save(self, *args, **kwargs):
        self.is_correct = (
            self.selected_answer.strip().lower()
            == self.question.correct_answer.strip().lower()
        )
        super().save(*args, **kwargs)
```

## Line-by-Line Explanation

### The `User` ForeignKey Pattern

```python
user = models.ForeignKey(
    settings.AUTH_USER_MODEL,    # 1
    on_delete=models.CASCADE,   # 2
    related_name="watch_history" # 3
)
```

**Line 1: `settings.AUTH_USER_MODEL`**

Why not just write `from django.contrib.auth.models import User` and use `User` directly?

Because if you ever swap Django's default `User` model for a custom one (e.g., to add a profile picture field), every `ForeignKey(User)` in your code breaks. `settings.AUTH_USER_MODEL` is a string reference (`"auth.User"` by default) that Django resolves at runtime — it always points to whatever User model is active, even if you change it later.

> [!TIP]
> **Always use `settings.AUTH_USER_MODEL`** for ForeignKey references to User.
> This is a Django best practice that will save you from a painful migration later.

**Line 2: `on_delete=models.CASCADE`**

This answers the question: "What happens to this row when the User it belongs to is deleted?"

| Option | Behavior | When to use |
|--------|----------|-------------|
| `CASCADE` | Delete this row too | Child data that's meaningless without its parent |
| `PROTECT` | Block the deletion | Data you must never accidentally lose |
| `SET_NULL` | Set the FK to NULL | Optional relationships (requires `null=True`) |
| `SET_DEFAULT` | Set to a default value | Rare — need a meaningful default |
| `DO_NOTHING` | Do nothing (can cause errors) | Almost never |

We use `CASCADE` because watch history entries, interests, and quiz attempts are meaningless without a user. Delete the user → delete all their data.

**Line 3: `related_name="watch_history"`**

This creates a **reverse relation**. Without it, you'd access a user's watch history as `user.watchhistoryentry_set.all()` (ugly). With it:

```python
# Forward: from child to parent
entry.user  # → the User object

# Reverse: from parent to children (thanks to related_name)
user.watch_history.all()  # → all WatchHistoryEntry objects for this user
```

### Field Types Deep Dive

| Field | SQL Type | Python Type | When to use |
|-------|----------|-------------|-------------|
| `CharField(max_length=N)` | `VARCHAR(N)` | `str` | Short text with a known max length |
| `TextField()` | `TEXT` | `str` | Long text (no max length) |
| `IntegerField()` | `INTEGER` | `int` | Whole numbers |
| `FloatField()` | `REAL` | `float` | Decimal numbers (use `DecimalField` for money) |
| `BooleanField()` | `BOOLEAN` | `bool` | True/False flags |
| `DateTimeField()` | `DATETIME` | `datetime` | Timestamps |
| `JSONField()` | `JSON` / `TEXT` | `dict` or `list` | Flexible structured data |
| `ForeignKey()` | `INTEGER + FK` | Model instance | Many-to-one relationship |

### Field Options

| Option | Meaning | Example |
|--------|---------|---------|
| `blank=True` | Field can be empty in **forms** | `channel_name = CharField(blank=True)` |
| `null=True` | Field can be `NULL` in the **database** | `watched_at = DateTimeField(null=True)` |
| `default=X` | Default value if none provided | `score = IntegerField(default=0)` |
| `auto_now_add=True` | Set to current time on creation (never changes) | `created_at = DateTimeField(auto_now_add=True)` |
| `auto_now=True` | Set to current time on every save | `updated_at = DateTimeField(auto_now=True)` |

> [!WARNING]
> **`blank` and `null` are different things!**
> - `blank=True` → validation only (forms accept empty strings)
> - `null=True` → database only (column allows NULL)
> - For `CharField`, use `blank=True` alone (empty string, not NULL)
> - For `DateTimeField`, use both `null=True, blank=True` (NULL in DB, optional in form)

### The `Meta` Inner Class

```python
class Meta:
    ordering = ["-weight"]
```

`Meta` configures table-level behavior (not column-level). Common options:

| Option | Purpose | Example |
|--------|---------|---------|
| `ordering` | Default sort order for queries | `["-weight"]` (descending by weight) |
| `verbose_name` | Human-readable name (singular) | `"watch history entry"` |
| `verbose_name_plural` | Human-readable name (plural) | `"watch history entries"` |
| `unique_together` | Compound unique constraints | `[("user", "label")]` |
| `db_table` | Override the auto-generated table name | `"my_custom_table"` |

### The `__str__` Method

```python
def __str__(self):
    return f"{self.video_title[:50]} ({self.channel_name})"
```

This controls how the object appears in:
- The admin site's list views
- The Django shell (`>>> print(entry)`)
- Debugging output
- Dropdown menus in the admin for ForeignKey fields

Without `__str__`, you'd see `WatchHistoryEntry object (1)` everywhere — useless.

### Overriding `save()` — Business Logic in the Model

```python
class Answer(models.Model):
    # ... fields ...

    def save(self, *args, **kwargs):
        self.is_correct = (
            self.selected_answer.strip().lower()
            == self.question.correct_answer.strip().lower()
        )
        super().save(*args, **kwargs)
```

This is a powerful pattern: **compute derived data automatically**.

- Every time an `Answer` is saved (created or updated), `is_correct` is recomputed
- The caller never has to remember to check correctness — it happens automatically
- `super().save(*args, **kwargs)` calls Django's default save (which actually writes to the database)

> [!IMPORTANT]
> **Always call `super().save()`** in your override, or the object won't actually be saved.
> The `*args, **kwargs` forwarding ensures Django's internal flags (like `update_fields`) still work.

## Register the App

Django doesn't know about `trivia` until you register it. Open `watchtrivia/settings.py` and find `INSTALLED_APPS`:

```python
INSTALLED_APPS = [
    'django.contrib.admin',          # The admin site
    'django.contrib.auth',           # User authentication
    'django.contrib.contenttypes',   # Framework for content types
    'django.contrib.sessions',       # Session management
    'django.contrib.messages',       # Flash messages
    'django.contrib.staticfiles',    # Serving CSS/JS/images

    # Third-party apps
    'rest_framework',                # Django REST Framework
    'corsheaders',                   # CORS headers for React

    # Our apps
    'trivia',                        # The Watchtrivia app
]
```

**Order matters for middleware but not for `INSTALLED_APPS`** (mostly). Convention is: Django built-ins first, then third-party, then your own.

### What does registering an app actually do?

When Django starts, it iterates through `INSTALLED_APPS` and for each one:

1. Imports the app's `apps.py` configuration
2. Discovers its `models.py` and registers the models with the ORM
3. Discovers its `admin.py` and registers admin classes
4. Discovers its `migrations/` directory for schema tracking
5. Makes the app's templates and static files findable

Skip this step and your models, admin registrations, and migrations are invisible to Django.

## Migrations — Version Control for Your Database

### What are migrations?

Every time you change a model (add a field, remove a field, change a field type), Django needs to update the database schema to match. **Migrations** are Python files that describe these schema changes.

### Step 1: Generate the migration

```powershell
python manage.py makemigrations trivia
```

This compares your current models to the last migration (or to nothing, if this is the first one) and generates a file like `trivia/migrations/0001_initial.py`:

```python
# Auto-generated — don't edit manually (usually)
class Migration(migrations.Migration):
    initial = True
    dependencies = [
        migrations.swappable_dependency(settings.AUTH_USER_MODEL),
    ]
    operations = [
        migrations.CreateModel(
            name='WatchHistoryEntry',
            fields=[
                ('id', models.BigAutoField(auto_created=True, primary_key=True)),
                ('video_title', models.CharField(max_length=500)),
                # ... etc
            ],
        ),
        # ... more CreateModel operations
    ]
```

### Step 2: Apply the migration

```powershell
python manage.py migrate
```

This runs all pending migrations — both Django's built-in ones (for `auth_user`, `django_session`, etc.) and yours. It executes the SQL to create the actual tables.

### The Migration Workflow

```
1. Edit models.py (add a field, change a type)
        ↓
2. python manage.py makemigrations
   → Generates a migration file in migrations/
        ↓
3. Review the migration file (optional but recommended)
        ↓
4. python manage.py migrate
   → Applies the SQL to the database
        ↓
5. Commit both models.py AND the migration file to Git
```

> [!IMPORTANT]
> **Always commit migration files to Git.** They're not generated build artifacts —
> they're the source of truth for your database schema history. Other developers
> (and your production server) need them to set up or update the database.

### Useful Migration Commands

| Command | Purpose |
|---------|---------|
| `python manage.py makemigrations` | Generate new migrations |
| `python manage.py migrate` | Apply all pending migrations |
| `python manage.py showmigrations` | List all migrations and their status |
| `python manage.py sqlmigrate trivia 0001` | Show the SQL a migration would run |
| `python manage.py migrate trivia 0001` | Migrate to a specific point (rollback) |

## The Admin Site

Django's admin site gives you a full CRUD (Create, Read, Update, Delete) interface for every registered model — for free. This is one of Django's killer features.

### Register Models with the Admin

Open `trivia/admin.py`:

```python
from django.contrib import admin
from .models import (
    WatchHistoryEntry,
    InterestTopic,
    Question,
    QuizAttempt,
    Answer
)


@admin.register(WatchHistoryEntry)
class WatchHistoryEntryAdmin(admin.ModelAdmin):
    list_display = ("video_title", "channel_name", "user", "watched_at")
    list_filter = ("user",)
    search_fields = ("video_title", "channel_name")


@admin.register(InterestTopic)
class InterestTopicAdmin(admin.ModelAdmin):
    list_display = ("label", "weight", "user")
    list_filter = ("user",)


@admin.register(Question)
class QuestionAdmin(admin.ModelAdmin):
    list_display = ("prompt_text", "topic", "user", "created_at")
    list_filter = ("topic",)


@admin.register(QuizAttempt)
class QuizAttemptAdmin(admin.ModelAdmin):
    list_display = ("user", "started_at", "completed_at", "score")


@admin.register(Answer)
class AnswerAdmin(admin.ModelAdmin):
    list_display = ("attempt", "question", "selected_answer", "is_correct")
```

### Admin Customization Options Explained

| Option | What it does | Example |
|--------|-------------|---------|
| `list_display` | Columns shown in the list view | `("video_title", "channel_name")` |
| `list_filter` | Sidebar filters for narrowing results | `("user",)` — filter by user |
| `search_fields` | Fields searchable via the search bar | `("video_title",)` — search titles |
| `list_per_page` | Rows per page (default: 100) | `list_per_page = 25` |
| `readonly_fields` | Fields that can't be edited | `("created_at",)` |
| `ordering` | Default sort in admin | `("-created_at",)` |
| `list_editable` | Fields editable directly in list view | `("weight",)` |
| `date_hierarchy` | Date-based drill-down navigation | `date_hierarchy = "watched_at"` |

### The `@admin.register` Decorator

This is syntactic sugar for:

```python
# These two are equivalent:

# Style 1: decorator (preferred)
@admin.register(WatchHistoryEntry)
class WatchHistoryEntryAdmin(admin.ModelAdmin):
    list_display = ("video_title",)

# Style 2: explicit registration
class WatchHistoryEntryAdmin(admin.ModelAdmin):
    list_display = ("video_title",)
admin.site.register(WatchHistoryEntry, WatchHistoryEntryAdmin)
```

## Playing with the ORM in the Shell

Django provides an interactive Python shell pre-loaded with your project:

```powershell
python manage.py shell
```

```python
# Import your models
from django.contrib.auth.models import User
from trivia.models import InterestTopic

# Create a user
user = User.objects.create_user(username="test", password="test123")

# Create an interest
topic = InterestTopic.objects.create(user=user, label="Formula 1", weight=0.85)

# Query all interests
InterestTopic.objects.all()
# <QuerySet [<InterestTopic: Formula 1 (0.85) - test>]>

# Filter
InterestTopic.objects.filter(weight__gte=0.5)  # weight >= 0.5

# Access the reverse relation
user.interests.all()
# <QuerySet [<InterestTopic: Formula 1 (0.85) - test>]>

# Update
topic.weight = 0.9
topic.save()

# Delete
topic.delete()
```

### Common ORM Query Patterns

| Pattern | Code | SQL Equivalent |
|---------|------|---------------|
| Get all | `Model.objects.all()` | `SELECT * FROM table` |
| Filter | `Model.objects.filter(field=val)` | `SELECT * WHERE field = val` |
| Exclude | `Model.objects.exclude(field=val)` | `SELECT * WHERE field != val` |
| Get one | `Model.objects.get(id=1)` | `SELECT * WHERE id = 1 LIMIT 1` |
| Count | `Model.objects.count()` | `SELECT COUNT(*) FROM table` |
| Order by | `Model.objects.order_by("-field")` | `SELECT * ORDER BY field DESC` |
| Exists | `Model.objects.filter(...).exists()` | `SELECT EXISTS(...)` |
| First | `Model.objects.first()` | `SELECT * LIMIT 1` |
| Lookup | `filter(weight__gte=0.5)` | `WHERE weight >= 0.5` |
| Contains | `filter(title__contains="F1")` | `WHERE title LIKE '%F1%'` |
| Starts with | `filter(title__startswith="F")` | `WHERE title LIKE 'F%'` |

### Field Lookups (the `__` syntax)

The double-underscore `__` is Django's way of expressing SQL operators:

| Lookup | Meaning | Example |
|--------|---------|---------|
| `__exact` | Exact match (default) | `filter(name__exact="F1")` |
| `__iexact` | Case-insensitive exact | `filter(name__iexact="f1")` |
| `__contains` | Contains substring | `filter(name__contains="F1")` |
| `__icontains` | Case-insensitive contains | `filter(name__icontains="f1")` |
| `__gt` / `__gte` | Greater than / greater or equal | `filter(weight__gte=0.5)` |
| `__lt` / `__lte` | Less than / less or equal | `filter(weight__lt=0.5)` |
| `__in` | In a list | `filter(id__in=[1, 2, 3])` |
| `__range` | Between two values | `filter(weight__range=(0.3, 0.8))` |
| `__isnull` | Is NULL | `filter(watched_at__isnull=True)` |

| Concept | What it means |
